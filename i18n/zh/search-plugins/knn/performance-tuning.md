# 性能调优

本主题提供性能调优建议，用于提高近似 k-NN（approximate k-NN，ANN）的索引和搜索性能。从整体上看，k-NN 按以下原则工作：
* 本地库索引按每个 knn_vector 字段 /（Lucene）段对创建。
* 查询在分片内按顺序在各个段上执行（与其他任何 OpenSearch 查询相同）。
* 段中的每个本地库索引返回 <=k 个邻居。
* 协调节点从每个分片返回的邻居中选取最终 size 数量的邻居。

本主题还提供了将近似 k-NN 与使用评分脚本的精确 k-NN 进行比较的建议。

## 索引性能调优

采取以下步骤来提高索引性能，尤其是在你计划一次性索引大量向量时：

* **禁用刷新间隔**

   禁用刷新间隔（默认值 = 1 秒），或为刷新间隔设置较长的时长，以避免创建多个小段：

   ```json
   PUT /<index_name>/_settings
   {
       "index" : {
           "refresh_interval" : "-1"
       }
   }
   ```
   **注意**：索引完成后，务必重新启用 `refresh_interval`。

* **禁用副本（不使用 OpenSearch 副本分片）**

   将副本数设置为 `0`，以避免在主分片和副本分片中重复构建本地库索引。索引完成后再启用副本时，序列化的本地库索引会被直接复制。如果没有副本，丢失节点可能会导致数据丢失，因此数据必须在其他地方另有存储，以便在出现问题时可以重试这次初始加载。

* **增加索引线程数**

   如果你选择的硬件有多个核心，可以在本地库索引构建中使用多个线程，从而加快索引过程。使用 [knn.algo_param.index_thread_qty](/search-plugins/knn/settings#cluster-settings) 设置确定要分配的线程数。

  请密切关注 CPU 使用率并选择合适的线程数。由于本地库索引构建的开销很大，使用多个线程可能会带来额外的 CPU 负载。

## 搜索性能调优

采取以下步骤来提高搜索性能：

* **减少段数量**

   为了提高搜索性能，必须控制段的数量。Lucene 的 IndexSearcher 会搜索分片中的所有段，以找出 'size' 个最佳结果。

   理想情况下，每个分片只有一个段，在搜索延迟方面可以提供最佳性能。你可以将索引配置为包含多个分片，以避免出现超大分片并获得更高的并行度。

   你可以通过选择更长的刷新间隔来控制段的数量，或者在索引期间通过禁用刷新间隔，让 OpenSearch 放慢段的创建。

* **预热索引**

   本地库索引在索引期间构建，但会在首次搜索时加载到内存中。在 Lucene 中，每个段按顺序进行搜索（因此对于 k-NN，每个段最多返回查询点的 k 个最近邻），然后在分片级别，从各段返回的所有结果中按评分返回前 'size' 个结果（评分越高 = 结果越好）。

   本地库索引加载后（本地库索引加载在 OpenSearch JVM 之外），OpenSearch 会将其缓存在内存中。最初的查询开销较大，需要几秒钟，而后续查询更快，只需几毫秒（假设未触发 k-NN 熔断器）。

   为了避免首次查询时的延迟损失，你可以对要搜索的索引使用预热（warmup）API 操作：

   ```json
   GET /_plugins/_knn/warmup/index1,index2,index3?pretty
   {
     "_shards" : {
       "total" : 6,
       "successful" : 6,
       "failed" : 0
     }
   }
   ```

   预热 API 操作会将指定索引所有分片（主分片和副本分片）的所有本地库索引加载到缓存中，因此在初始搜索时不会因加载本地库索引而产生损失。

   **注意**：此 API 操作只会将它***看到的***索引段加载到缓存中。如果在 API 运行之后有合并或刷新操作完成，或者你添加了新文档，则需要重新运行该 API，将这些本地库索引加载到内存中。

* **避免读取存储字段**

   如果你的用例只是读取最近邻的 ID 和评分，可以禁用读取存储字段，从而节省从存储字段中检索向量的时间。

* **使用 `mmap` 文件 I/O**

   对于基于 Lucene 的近似 k-NN 搜索，没有专门用于加速读写操作的缓存层。相反，该插件依赖 OpenSearch 核心中现有的缓存机制。在 2.4 及更早版本的基于 Lucene 的近似 k-NN 搜索中，读写操作默认基于 Java NIO，速度可能较慢，具体取决于 Lucene 版本和每个分片的段数。从 2.5 版本开始，当存储类型为 `hybridfs`（OpenSearch 中的默认存储类型）时，k-NN 默认启用 [`mmap`](https://en.wikipedia.org/wiki/Mmap) 文件 I/O。这样可以实现快速的文件 I/O 操作，并提高数据摄取和搜索的整体性能。使用 `mmap` 的两个向量值专用文件扩展名是 `.vec` 和 `.vem`。有关这些文件扩展名的更多信息，请参阅 [Lucene 文档](https://lucene.apache.org/core/9_0_0/core/org/apache/lucene/codecs/lucene90/Lucene90HnswVectorsFormat.html)。

   `mmap` 文件 I/O 使用系统文件缓存，而不是为 Java 堆分配的内存，因此不需要额外分配内存。要更改插件设置的默认扩展名列表，请使用[集群设置 API](/api-reference/cluster-api/cluster-settings) 在集群级别更新 `index.store.hybrid.mmap.extensions` 设置。**注意**：这是一项专家级设置，更新前需要关闭索引，更新后再重新打开。

## 提高召回率

召回率取决于多种因素，例如向量数量、维度数、段等。在大量小段上搜索并聚合结果，比在少量大段上搜索并聚合结果能获得更好的召回率。本地库索引越大，如果使用较小的算法参数，召回率下降的可能性就越大。为算法参数选择较大的值应该有助于解决这个问题，但会牺牲搜索延迟和索引时间。因此，重要的是了解系统对延迟和精度的要求，然后基于实验来选择索引应包含的段数。

默认参数适用于较广泛的用例，但请务必在自己的数据集上进行实验并选择合适的值。有关索引级设置，请参阅[索引设置](/search-plugins/knn/knn-index#index-settings)。

## 近似最近邻与评分脚本的对比

标准 k-NN 查询和自定义评分选项的性能表现不同。请使用一组有代表性的文档进行测试，看看搜索结果和延迟是否符合你的预期。

如果初始过滤器能将文档数量减少到不超过 20,000 个，则自定义评分的效果最好。增加分片数可以改善延迟，但请确保分片大小保持在[推荐的指导范围](/intro#primary-and-replica-shards)内。
